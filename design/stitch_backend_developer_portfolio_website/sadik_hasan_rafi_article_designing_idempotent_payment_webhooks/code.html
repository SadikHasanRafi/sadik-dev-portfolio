01 / The Vulnerability

The Burst Failure Vulnerability in Multi-Gateway Settlement

In high-velocity commerce and fintech environments, webhook delivery is fundamentally built on an asynchronous, unreliable transport: at-least-once HTTP delivery. Payment aggregators including Stripe, bKash, SSLCommerz, and Nagad specify guarantees that if your ingress server responds with anything other than an unequivocal 200 OK within 3 to 5 seconds, an immediate retry storm is triggered.

When an upstream network timeout occurs—or your application cluster experiences a sudden garbage collection pause or downstream database connection pool saturation—the payment gateway fires an exponential burst. In our production audit, we observed upstream providers dispatching up to 8 duplicate webhook payloads within 400 milliseconds for a single payment reference.

Production Critical Incident Vector

If two separate worker threads pull the duplicate webhook requests concurrently, both queries check the ledger: both find no prior fulfillment record, both credit the customer account balance, and both execute irrevocable inventory decrement mutations. The result: financial double-crediting and ledger divergence.

02 / Deterministic Identity

Deterministic Payload Fingerprinting via SHA-256 HMAC

Many naive implementations rely solely on the webhook event ID provided in the header (evt_xxx). However, during regional network failovers, legacy gateways frequently re-issue payments under new synthetic identifiers while retaining the identical transaction payload.

To achieve absolute idempotency, we build a compound deterministic fingerprint. We normalize the body keys alphabetically, concatenate the gateway timestamp, transaction reference, amount, and currency, and hash them with a cluster-shared secret HMAC.

04 / ACID Enforcement

Preventing Phantom Reads Under Repeatable Read Isolation

In default PostgreSQL isolation (READ COMMITTED), each statement takes its own snapshot of database state. This creates an insidious window for a race condition: Worker A reads the ledger, Worker B commits an insert, Worker A reads again and executes a double-write without violating foreign key constraints.

By lifting the transaction isolation level to REPEATABLE READ combined with a unique composite index across (gateway_code, transaction_id, amount), PostgreSQL raises a serialization anomaly error (40001) if any interleaved write attempts to tamper with the lock boundary.

06 / Operational Resilience

Dead-Letter Queues (DLQ) & Automated Pager Alerts

What happens when an upstream provider sends a genuine malformed JSON string, or a network partition severs our PostgreSQL replica during settlement?

Instead of dropping the request or entering an infinite retry loop with the gateway, the ingress service automatically traps the non-idempotent payload and offloads it to a BullMQ Dead-Letter Queue (DLQ) backed by Redis Streams.

  • Exponential Jitter Backoff: Retries are executed at 2s, 8s, 32s, 128s with a 15% random jitter factor to avoid thundering-herd effects on recovery.
  • Poison-Pill Quarantine: Any payload failing 5 sequential execution passes is moved into an immutable quarantine table with full headers, payload dump, and stack trace.
  • PagerDuty P1 Hook: If the DLQ ingestion rate exceeds 3 events in a rolling 60-second window, automated alert webhooks page the on-call systems architect.
