SECTION 01 / RACE CONDITIONS

The Burst Failure Vulnerability in Multi-Gateway Settlement

In modern financial rails (Stripe, Adyen, Razorpay), network timeouts are inevitable. When a gateway sends an HTTP webhook notification of a captured charge and receives an ephemeral 504 Gateway Timeout from an intermediate proxy, its automated exponential backoff triggers an immediate retry.

warning
PRODUCTION CRITICAL INCIDENT VECTOR

If two worker threads pull identical webhook payloads concurrently, both query the payment ledger before either commits. Finding no ledger entry, both dispatch fulfillment and credit the merchant balance twice.

SECTION 03 / IMPLEMENTATION

Distributed Mutex via Redis SET NX PX & PostgreSQL Upsert

Below is the core TypeScript implementation running inside Rafi’s transaction orchestration services. It treats concurrency as an absolute inevitability rather than an edge-case anomaly.

idempotent-worker.ts
// 1. Atomic Distributed Lock Acquisition
const lockKey = `lock:webhook:${fingerprint}`;
const acquired = await redis.set(
  lockKey, workerId, 'PX', 60000, 'NX'
);

if (!acquired) {
  // Another worker is already processing this exact event
  return { status: 'CONCURRENT_SKIP', ack: true };
}

// 2. PostgreSQL REPEATABLE READ Guard
try {
  await db.transaction({
    isolationLevel: 'REPEATABLE READ'
  }, async (tx) => {
    const existing = await tx.idempotencyLedger.findUnique({
      where: { hash: fingerprint }
    });
    if (existing) return;

    await tx.idempotencyLedger.create({
      data: { hash: fingerprint, status: 'COMMITTED' }
    });
    await creditMerchantBalance(tx, payload);
  });
} finally {
  // Safe release via Lua script comparison
  await releaseSafeRedisLock(redis, lockKey, workerId);
}
SECTION 04 / DATA INTEGRITY

Preventing Phantom Reads Under Repeatable Read Isolation

Standard READ COMMITTED is inadequate for asynchronous payment processors. If worker A performs an upsert check while worker B is midway through writing a balance credit, phantom reads allow both to succeed.

verified_user The Double-Tiered Invariant Guarantee

PostgreSQL enforces unique constraints on the primary hash key at engine level. If an overlap passes through Redis lock degradation (e.g. cluster node rollover), the database throws error code 23505 (unique_violation), aborting the secondary transaction safely with 0 side-effects.
